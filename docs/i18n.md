## 一、i18n 机制说明

### 目录结构

所有语言文件位于 `assets/i18n/` 目录：

- `index.json`：语言注册表，`files` 数组列出所有可用的语言文件名
- `{code}.json`：每种语言一个文件，文件名即语言代码（如 `zh-cn.json`）

当前注册表内容：

```json
{
  "files": ["en-us.json", "zh-cn.json"]
}
```

### 文件结构

每个 `{code}.json` 的结构如下：

```json
{
  "meta": {
    "code": "zh-cn",
    "name": "简体中文"
  },
  "strings": {
    "index": { "...": "..." },
    "help": { "...": "..." }
  }
}
```

- `meta.code`：语言代码，一律小写。运行时优先以它为语言标识
- `meta.name`：语言的本地显示名称，用于语言切换下拉框
- `strings`：翻译内容的完整树，按页面分组（`index` 与 `help` 两页）

### 键路径

- 字符串通过点分路径定位，例如 `index.actions.reloadData`
- 模板参数用 `{param}` 占位，运行时替换为实际值，例如 `status.loadingAlgorithm` 的值是 `"Loading {algorithm}..."`
- 英语（en-us）是回退语言：当前语言缺键时自动回退到英文，英文也没有时才显示 fallback 或键名本身

### 使用方式

- HTML：`data-i18n`（替换文本）、`data-i18n-html`（替换 HTML 片段）、`data-i18n-title`（替换 title 属性）、`data-i18n-placeholder`（替换 placeholder）、`data-i18n-aria-label`（替换无障碍标签）
- JS：`t(key, fallback, params)` 读取并格式化字符串

index.html 中的示例：

```html
<p class="eyebrow" data-i18n="index.hero.eyebrow">Dashboard</p>
<button type="button" data-i18n-title="common.switchLanguage">🌐</button>
<button type="button" data-i18n="index.actions.reloadData">Reload Data</button>
```

help.html 同样通过 `data-i18n` 系列属性工作，初始化时传入 `page: "help"`，键前缀为 `help.*`。

### 语言选择优先级

初始化时按以下候选顺序匹配：URL 的 `?lang=` 参数 → 浏览器 `navigator.languages` → localStorage（键 `benchmark.language`）→ 默认语言。匹配支持 BCP-47 前缀，例如候选 `zh` 可以命中 `zh-cn`。

## 二、贡献方法

### 新增语言

1. 复制 `assets/i18n/en-us.json` 为 `assets/i18n/{code}.json`
2. 修改 `meta`：`code` 改为目标语言代码（小写），`name` 改为该语言的本地显示名称
3. 在 `assets/i18n/index.json` 的 `files` 数组中注册新文件名
4. 翻译 `strings` 全树：index 页与 help 页两页的键都要覆盖
5. 保持键结构与 en-us.json 完全同步；缺键会回退英文，但不应依赖回退

### 修改文案

- 直接修改 `assets/i18n/{code}.json` 中对应键的文本即可
- 若键名或路径需要变更，必须同步更新 en-us.json、所有语言文件，以及引用该键的 HTML 与 JS

### PR 流程

1. 创建分支，只提交 `assets/i18n/` 目录下的变更（语言文件 + index.json）
2. 在 PR 描述中说明新增或修改的语言与内容
3. 提交前自查：键结构是否与 en-us.json 同步、JSON 是否合法、译文是否准确通顺

## 三、规范

- 语言代码用小写 BCP-47 风格，例如 `zh-cn`、`ja`、`ko`
- 文件名必须等于语言代码（`{code}.json`）
- 不提交机器翻译，译文应由母语者校对
- en-us.json 始终为基准：所有语言文件必须与它保持键结构一致

## 1. How i18n works

### Directory layout

Language files live in `assets/i18n/`:

- `index.json` is the registry. Its `files` array lists every available language file.
- `{code}.json` holds one language per file. The file name is the language code, e.g. `zh-cn.json`.

Current registry content:

```json
{
  "files": ["en-us.json", "zh-cn.json"]
}
```

### File shape

Every `{code}.json` has the same shape:

```json
{
  "meta": {
    "code": "zh-cn",
    "name": "简体中文"
  },
  "strings": {
    "index": { "...": "..." },
    "help": { "...": "..." }
  }
}
```

- `meta.code` is the language code, always lowercase. The runtime trusts it over the file name.
- `meta.name` is the localized display name, shown in the language switcher dropdown.
- `strings` is the full translation tree, grouped by page (`index` and `help`).

### Key paths

- Strings are located by dotted paths, e.g. `index.actions.reloadData`.
- Template parameters use `{param}` placeholders, replaced at runtime. For example `status.loadingAlgorithm` holds `"Loading {algorithm}..."`.
- English (en-us) is the fallback language. A missing key in the active language falls back to English; only when English is missing too does the code show the fallback argument or the raw key.

### Usage

- HTML attributes: `data-i18n` (text), `data-i18n-html` (HTML fragment), `data-i18n-title` (title attribute), `data-i18n-placeholder` (placeholder), `data-i18n-aria-label` (accessibility label).
- JS: `t(key, fallback, params)` reads and formats a string.

Examples from index.html:

```html
<p class="eyebrow" data-i18n="index.hero.eyebrow">Dashboard</p>
<button type="button" data-i18n-title="common.switchLanguage">🌐</button>
<button type="button" data-i18n="index.actions.reloadData">Reload Data</button>
```

help.html works the same way with `data-i18n` attributes. It initializes with `page: "help"`, so its keys use the `help.*` prefix.

### Language detection order

At startup the code tries candidates in this order: the `?lang=` URL parameter, `navigator.languages`, localStorage (key `benchmark.language`), then the default language. Matching is BCP-47 prefix aware, so a candidate like `zh` can match `zh-cn`.

## 2. How to contribute

### Adding a language

1. Copy `assets/i18n/en-us.json` to `assets/i18n/{code}.json`.
2. Change `meta`: set `code` to the target language code (lowercase) and `name` to its localized display name.
3. Register the new file name in the `files` array of `assets/i18n/index.json`.
4. Translate the whole `strings` tree. Cover the keys for both the index page and the help page.
5. Keep the key structure fully in sync with en-us.json. Missing keys fall back to English, but you should not rely on that.

### Editing copy

- To change a string, edit the matching key in `assets/i18n/{code}.json`.
- If a key name or path must change, update en-us.json, every language file, and the HTML or JS that references the key.

### PR flow

1. Create a branch and commit only changes under `assets/i18n/` (language files plus index.json).
2. Describe in the PR which language was added or what copy changed.
3. Self-check before submitting: the key structure matches en-us.json, the JSON is valid, and the translations read naturally.

## 3. Conventions

- Use lowercase BCP-47 style codes, e.g. `zh-cn`, `ja`, `ko`.
- The file name must equal the language code (`{code}.json`).
- Do not commit machine translations; have a native speaker review the copy.
- en-us.json is always the baseline. Every language file must keep the same key structure as it does.
